Principes incontournables

Règle d’or : « N’utilisez pas ARIA si vous pouvez faire autrement. » Une balise native avec une sémantique correcte restera toujours plus fiable qu’un rôle ARIA appliqué sur une balise neutre.

  • ARIA ne change pas le comportement du navigateur, mais fournit une information complémentaire aux technologies d’assistance.
  • Respectez la structure hiérarchique des rôles : certains sont parents/enfants.
  • Tout rôle interactif personnalisé doit s’accompagner d’une gestion clavier cohérente.
  • Les attributs ARIA doivent être synchronisés en temps réel avec l’état visuel du widget.

Différences ARIA / HTML

Les éléments HTML ont une sémantique implicite. Ajouter un rôle explicite sur une balise qui possède déjà un rôle peut poser des problèmes. Utilisez les attributs ARIA pour compléter, pas pour remplacer.

Quand utiliser un rôle

  • Pour décrire un composant personnalisé (ex. : div transformée en bouton).
  • Pour baliser une zone logique (landmark) lorsqu’aucune balise native n’est disponible.
  • Pour préciser une relation (ex. : aria-labelledby).

Anti-patterns courants

  • Ajouter role="button" sans gérer Enter et Space.
  • Empiler les rôles (ex. : role="navigation" sur un nav).
  • Utiliser aria-hidden="true" sur un élément focusable.
  • Masquer du texte visuel sans alternative pour lecteur d’écran.

Landmarks ARIA

Les landmarks facilitent la navigation rapide des utilisateurs de lecteurs d’écran. Utilisez les balises HTML5 natifs en priorité (ex. : header, main, nav, aside, footer).

Landmarks essentiels
Rôle Quand l’utiliser Bonnes pratiques Exemple
banner En-tête principal du site, unique par page. Utiliser <header> au niveau racine. <header role="banner">...</header>
navigation Menu principal ou secondaire répété. Préciser un libellé avec aria-label. <nav aria-label="Navigation principale">
main Contenu principal unique. Un seul <main> ou role="main" par page. <main id="contenu" role="main">
complementary Contenu secondaire lié au principal (ex. : encadré). Ne pas dupliquer le contenu principal. <aside role="complementary" aria-label="Sommaire">
contentinfo Pied de page global du site. Disponible via <footer> sur la page. <footer role="contentinfo">

Structure documentaire et relations

Hiérarchie de titres

  • Un seul <h1> par page.
  • Progression logique h2 → h3 sans sauts injustifiés.
  • Les titres de sections doivent précéder les contenus correspondants.

Relations ARIA

  • aria-labelledby pour lier un titre à un widget ou une section.
  • aria-describedby pour fournir une aide supplémentaire.
  • aria-controls pour indiquer la cible d’une action (toggle, tab).
<section aria-labelledby="faq-title">
  <h2 id="faq-title">Questions fréquentes</h2>
  <p id="faq-help">Utilisez les flèches pour naviguer entre les questions.</p>
  <ul role="listbox" aria-describedby="faq-help">
    <li role="option" aria-selected="true">Pourquoi déployer un DOA ?</li>
    <li role="option">Comment tester un lecteur d’écran ?</li>
  </ul>
</section>

Widgets ARIA & interactions clavier

Chaque widget personnalisé doit reproduire les interactions natives. Le tableau ci-dessous synthétise les comportements requis.

Widgets interactifs
Pattern Rôles & attributs Interactions clavier Points RGAA
Onglets role="tablist", role="tab", aria-controls, aria-selected.
  • Tab circule entre l’ensemble.
  • Flèche droite/gauche change d’onglet.
  • Home/End aller au premier/dernier.
 Critères RGAA 9.2, 9.3, 7.3.
Accordéon role="button", aria-expanded, aria-controls, panel avec role="region".
  • Enter/Space ouvre/ferme.
  • Tab circule, Shift+Tab permet retour.
 Critères 7.1, 7.3, 13.3.
Menu role="menubar", role="menuitem", aria-haspopup, aria-expanded.
  • Alt + M pour focus (si raccourci).
  • Flèches se déplacer, Enter active.
  • Esc ferme le menu.
 Critères 7.4, 8.2, 9.3.
Dialog modal role="dialog" ou alertdialog, aria-modal="true", focus trap, aria-labelledby.
  • Focus sur le premier élément interactif.
  • Esc ferme, focus retour sur l’appelant.
 Critères 11.5, 11.6, 7.3.

Live regions

Les live regions annoncent automatiquement des changements de contenu. Choisissez le niveau d’annonce en fonction de la criticité.

Types de live regions
Attribut Usage Exemple
aria-live="polite" Notifications non critiques (tâches terminées, messages info). <div aria-live="polite">Profil mis à jour.</div>
aria-live="assertive" Alertes prioritaires (erreurs bloquantes, sessions expirées). <div role="alert">Votre session a expiré.</div>
aria-live="off" Désactiver l’annonce (par défaut). <div aria-live="off">...</div>

Bonnes pratiques :

  • Positionnez la live region dans le DOM avant le script qui la met à jour.
  • Utilisez aria-atomic="true" pour annoncer le bloc entier.
  • Ne surchargez pas les utilisateurs avec trop d’annonces.

États et propriétés ARIA

Les états (aria-checked, aria-expanded, etc.) et les propriétés (aria-haspopup, aria-controls) doivent refléter l’état visuel du composant. Ils sont indispensables pour certains widgets.

Récapitulatif des attributs critiques
Attribut Quand l’utiliser Valeurs valides Exemple
aria-expanded Accordéons, menus, widgets dépliables. true, false, undefined. <button aria-expanded="false" aria-controls="faq1">
aria-pressed Boutons toggle, boutons radio personnalisés. true, false, mixed. <button role="button" aria-pressed="mixed">
aria-invalid Champs de formulaire en erreur. true, false, grammar, spelling. <input aria-invalid="true" aria-describedby="email-erreur">
aria-current Élément actif dans une navigation ou un listing. page, step, true, etc. <li aria-current="page"><a href="/contact">Contact</a></li>
aria-describedby Associer une aide contextuelle, un message d’erreur. Identifiant d’un ou plusieurs éléments. <input aria-describedby="hint-contraste">

Tests et diagnostics

Méthodes manuelles

  • Tester au clavier : ordre logique, absence de piège, focus visible.
  • Utiliser NVDA (Windows) ou VoiceOver (macOS) pour vérifier l’annonce des rôles/états.
  • Vérifier les relations aria-labelledby et aria-describedby.

Tests automatisés

  • axe DevTools ou aXe-core pour intégrer dans Cypress/Jest.
  • Pa11y CI, Lighthouse CI pour pipeline.
  • Linting avec @angular-eslint, eslint-plugin-jsx-a11y.

Checklist rapide :

  • Les rôles correspondent-ils à la fonction du composant ?
  • Les attributs aria-* sont-ils mis à jour dynamiquement ?
  • La navigation au clavier est-elle intuitive et documentée ?
  • Les erreurs sont-elles restituées via aria-live ou role="alert" ?
